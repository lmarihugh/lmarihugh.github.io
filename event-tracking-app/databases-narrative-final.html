Event Tracking App Narrative: Databases

Why I chose this artifact, how the enhancement improved it, and what I learned along the way.

← Back to the Event Tracking App overview

1. The artifact

This artifact for the databases category is the Event Tracking app. It is a Java based Android app that was originally built for CS 360. The app is designed to track events and notify a user. It holds a login page, dashboard, and event editor/creator. There is additional functionality for a SMS reminder but this was not the focus of my project enhancements.

2. Why it is in my portfolio and how it was improved

The Event Tracking app belongs in my ePortfolio because the original database was very basic and had minimal security, therefore had many opportunities for improvement. It allowed me to evaluate a system already working and then fix it. The changes I made were:

  • Salted password hashing. This changed the original storage of passwords from plain text to a random 16 byte salt per user and then hashed the password.
  • PBKDF2. Originally I planned on doing SHA-256 but swapped to PBKDF2 because it made each guess harder.
  • A foreign key. I changed events.username to be a foreign key to users.username, so an event won't be able to exist for a user who isn't there, and deleting a user deletes their events too.
  • An index. I added an index to events.username.

3. Testing

My feedback from Milestone Four was that the narrative needed more detail on the challenges during testing, so here are more details. The first time I ran the version 2 app, it crashed, so I used the Logcat tool within Android Studio to read the exception. The failures were emulator install errors, which didn't have anything to do with the code. I was able to fix these, and some had to do with the project structure, but it was very helpful to have tools like Logcat to help identify them.

In addition to the above, while finishing the final version, I did find a bug within my code. The migration hashed every existing user's password, while PBKDF2 refused to hash an empty password, so the app crashed during the upgrade whenever an empty one appeared. Logcat also showed this exception, and I figured out that it was coming from the migration. I fixed it by adding a fixed prefix to every password before it is hashed, to make sure the input was not empty.

I also ran 6 automated repository tests that covered the database rules, to ensure users only see their own events, deleting a user also deletes their events, and so on.

4. Reflection

What I learned

Overall, I did pretty well with the building, but the testing did teach me that a crash is not always a code issue. Utilizing the tools within the environment you are using can be very helpful and leave you working efficiently rather than reading lines and lines of code or guessing.

Challenges

Separating the two testing errors and trying to figure out why something was happening was super challenging for me. It took me an embarrassing amount of time trying to figure out Logcat.

Feedback

The feedback I received initially was to add more detail to my testing notes and explain further.

Course outcomes

Using well founded techniques and tools to deliver value was one I believe I succeeded in by applying standard database practices and using Logcat. I also met Outcome 5, the security mindset, because I was focused on updating the plain text credentials to fix a true vulnerability. Outcomes 1 and 2 were not the focus here and Outcome 3 was covered by my other enhancements.

Software Design and Engineering

Event Tracking App Narrative: Software Design

Why I chose this artifact, how the enhancement improved it, and what I learned along the way.

← Back to the Event Tracking App overview

1. The artifact

This artifact for the software design and engineering category is the Event Tracking app. It is a Java based Android app that was originally built for CS 360. The app is designed to track events and notify a user. It holds a login page, dashboard, and event editor/creator. There is additional functionality for a SMS reminder but this was not the focus of my project enhancements.

2. Why it is in my portfolio and how it was improved

This artifact is a mobile app that showcases multiple layers of software development that I created. I believe it is a very thorough presentation of my skills. In addition, there were very clear weaknesses that allowed me to prove my skill. For example, the dashboard screen was hardcoded with event slots which would not allow for scale. The changes I implemented were:

  • An Event class. I added an Event class to represent a single event as a structured object rather than the four array slots.
  • A repository. I built the EventRepository to own all access to the database.
  • A RecyclerView. I fixed the hardcoded dashboard screen with a RecyclerView and EventAdapter.
  • Validation. I added in validation to the creation and editing of events, which exists in the EventValidator class.

3. Testing

My feedback from the professor in Milestone Two was to expand testing, specifically with the repository operations and validation, so I wrote automated tests for both.

  • EventValidatorTest, JUnit, runs 10 different tests. It covers empty or blank titles, validates dates and times, checks for impossible dates such as leap years or a 24 hour time, and then empty or null inputs.
  • EventRepositoryTest, runs through the emulator, 6 tests. This covers deleting events, tests users' visibility into only their events, and rejection of an event for a user that doesn't exist.

To complete the testing, I moved the validation into EventValidator to ensure it was testable. For the repository, I needed to add a second constructor to EventRepository and DatabaseHelper so it will pass its own database. Besides the two automated tests, I ran the finished app on the emulator multiple times and tested both invalid and valid inputs, editing events, saving, etc.

4. Reflection

What I learned

The major thing I learned was separating issues for this project because I needed to separate things specifically for the software design and engineering side, but I used this same project for the database section. In addition to that, the EventRepository took away any database calls which made the Dashboard and Event screens much simpler. Writing the tests also helped me because once I set the validation and database access as separate pieces, each could be tested on its own.

Challenges

My biggest challenge was still the one I found when I did the milestone. I initially rewrote in VS instead of Android Studio so I needed to rebuild the whole project into Android Studio. However, that was not an issue for the enhancements.

Feedback

The feedback I received, that I also stated above, was that I needed to expand the testing. I did that by adding 10 validation tests and 6 repository tests.

Course outcomes

I planned this enhancement to demonstrate designing and evaluating computing solutions while managing the tradeoffs, as well as using the well founded techniques I've learned. I believe both were fully met. I moved the hardcoded array to a single event model. The RecyclerView was a design tradeoff for a more up front structure but it eliminated potential bugs. Adding in the automated tests and validations also further prove that I met these outcomes.
